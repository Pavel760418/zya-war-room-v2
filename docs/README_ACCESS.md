# Как открыть МегаМетрики из офиса

Короткая инструкция для сотрудников. Логин и пароль **не нужны**.

---

## Что нужно

1. Ноутбук или компьютер с браузером (Chrome, Edge или Яндекс.Браузер).
2. Подключение к **корпоративному Wi‑Fi офиса** (тот же, через который открываются внутренние системы).
3. Если вы не в офисе — корпоративный VPN (если его выдала ИТ-служба). С домашнего мобильного интернета внутренний адрес обычно не открывается.

---

## Ссылка на приложение

Скопируйте целиком в адресную строку браузера:

**http://192.168.2.95:8080/**

Нажмите Enter. Должна открыться страница **«МегаМетрики — Панель управления сетью»**.

### Со смартфона (iPhone / Android)

Офисный адрес `192.168.2.95:8080` с гостевого Wi‑Fi `10.15.0.0/24` часто **не маршрутизируется** до сервера.

**Не открывайте** `http://81.163.35.181:3000/` и `...:3000/mega/` — с интернета порт 3000 всё ещё ведёт на **Metabase** на другой машине (этот сервер запросы с телефона не получает). Очистка Safari это не меняет.

Временная ссылка МегаМетрики (другой адрес, без Metabase):

**https://30b10eeeacdb8b.lhr.life/**

Логин не нужен. Если Safari спросит про сайт — откройте. Не нажимайте старую иконку Metabase на экране «Домой».

---

## Если страница не открывается

1. Убедитесь, что вы подключены к **корпоративному Wi‑Fi**, а не к мобильному интернету телефона и не к домашней сети.
2. Обновите страницу (клавиша F5) или попробуйте другой браузер.
3. Если видите ошибку соединения / «сайт недоступен» — напишите в поддержку (ниже) и приложите **точный текст ошибки** и скриншот.

---

## Куда писать, если нужна помощь

Напишите в общий чат тестирования МегаМетрики или в ИТ-поддержку:

> Не открывается МегаМетрики по ссылке http://192.168.2.95:8080/  
> + скрин ошибки + откуда заходите (офисный Wi‑Fi / VPN / другое)

Для прогона коллегами (чек-лист и шаблон обратной связи): см. [`docs/INSTRUKCIYA_TESTIROVANIE.md`](INSTRUKCIYA_TESTIROVANIE.md).

## Для ИТ / сетевого администратора (служебный блок)

### Результат сетевой проверки (сервер приложения `192.168.2.95`)

| Проверка | Результат |
|----------|-----------|
| Адрес сервера приложения | `192.168.2.95/24` (порт UI через nginx `:8080`) |
| Маршрут к корпоративному Wi‑Fi `10.100.0.0/23` | Есть: `10.100.0.132 via 192.168.2.253` |
| Сеть Wi‑Fi `10.15.0.0/24` (шлюз `10.15.0.1`, хост `10.15.0.29`, BSSID `D2:67:2D:63:0B:0B`) | Allowlist nginx добавлен; ICMP с сервера не отвечает (редирект на `192.168.2.203`) |
| ICMP до шлюза Wi‑Fi `10.100.0.1` | OK (rtt ~1.7 ms) |
| ICMP до хоста `10.100.0.132` | Нет ответа (часто хост режет ping — не доказательство отсутствия маршрута) |
| HTTP `http://192.168.2.95:8080/` с сервера | HTTP **200** |
| Allowlist nginx для Wi‑Fi | `10.100.0.0/23`, `10.100.0.132`, `10.15.0.0/24`, `10.15.0.29` |

**Вывод:** маршрутизация между `10.100.0.0/23` и `192.168.2.0/24` на уровне сети **настроена** (подтверждено маршрутом и ping до шлюза Wi‑Fi). Прямой доступ сотрудников к UI должен работать с корпоративного Wi‑Fi по ссылке выше.

Если у конкретного сотрудника всё же таймаут/нет соединения (не ошибка 403), передайте сетевому инженеру запрос:

> Открыть маршрут/правило firewall между VLAN `10.100.0.0/23` / `10.15.0.0/24` и хостом `192.168.2.95` на порт `8080` (TCP).

При ответе **403 Forbidden** — проблема в allowlist nginx (не в маршрутизации); проверить `allow 10.100.0.0/23` и `allow 10.15.0.0/24` в `deploy/edge/nginx.conf`.

### Кэш и расписание (служебно)

- Пользовательский UI читает SQLite-кэш (`WARROOM_DATA_SOURCE=cache`), не MSSQL 1С.
- Синхронизация: user systemd `warroom-sync.timer` (**08:00 и 12:00 МСК** / Europe/Moscow), `Linger=yes` — переживает logout.
- Лог: `/home/andr/apps/zya-war-room-v2/var/log/sync_from_1c.log`
- Кэш: `/home/andr/apps/zya-war-room-v2/var/cache/warroom_raw.sqlite`
